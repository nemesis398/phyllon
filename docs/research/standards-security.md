# Standards and Security

Checked on 2026-10-29 against primary sources (standards bodies, specs, official docs, release feeds, advisory databases). Each fact carries a source URL and a confidence mark:

- **primary**: verified in the governing document, official docs, source code or a registry or release feed.
- **secondary**: from a law-firm note, blog, vendor summary or other third party.
- **unverified**: inferred, remembered, or not found. Treat as a hypothesis.

Tool versions come from GitHub release feeds, crates.io and the Rust dist manifest on the check date. Where I judge rather than report, the text says "Implication" or "Inference". Phyllon facts come from the project brief, not from code.

## 1. Web application security

### Facts

- OWASP ASVS (Application Security Verification Standard) 5.0.0 is the current stable release, published 30 May 2025. The project page lists no 5.1. A "bleeding edge" build regenerated on 2026-10-26 is preview only. Sources: https://asvs.owasp.org/, https://github.com/OWASP/ASVS/releases. Confidence: primary.
- ASVS 5.0 has about 350 requirements in 17 chapters. Level 1 holds about 20%, level 2 about 50% (so level 2 compliance means about 70% of all requirements), level 3 about 30%. The text says "Most applications should be striving to achieve" level 2, and leaves the choice to the organization's risk analysis. It does not mention children's data. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x03-What-is-the-ASVS.md. Confidence: primary.
- ASVS 5.0 requirements are phrased as "must", and some chapters start with documentation requirements (for example 5.1.1: document permitted file types, extensions and maximum unpacked size per upload feature). Source: same file, plus https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md. Confidence: primary.
- Chapter V10 (OAuth and OIDC) has sections for the OAuth client, the resource server, the authorization server, the OIDC client, the OpenID Provider and consent. Phyllon plays three of these roles (authorization server, resource server, later OIDC client). Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x19-V10-OAuth-and-OIDC.md. Confidence: primary.
- V10 requirements and levels that bind Phyllon's authorization server: 10.4.1 exact redirect URI match (L1), 10.4.2 single-use code (L1), 10.4.3 code lifetime at most 10 minutes (L1), 10.4.4 only the grants a client needs, no implicit or password grant (L1), 10.4.5 refresh token replay mitigation (L1), 10.4.6 PKCE (L2), 10.4.7 unauthenticated dynamic client registration must validate metadata, obtain consent and warn about untrusted clients (L2), 10.4.8 absolute refresh token expiry (L2), 10.4.9 revocation by the user in the authorization server UI (L2), 10.4.11 only required scopes per client (L2), 10.7.1 to 10.7.3 consent shown, reviewable and revocable (L2). Resource server: 10.3.1 audience check (L2), 10.3.2 authorize from token claims (L2), 10.3.5 sender-constrained tokens (L3). OIDC client: 10.5.1 nonce (L2), 10.5.2 identify users by `sub` (L2), 10.5.3 reject metadata whose issuer differs (L2), 10.5.4 `aud` equals `client_id` (L2). Source: same V10 file. Confidence: primary.
- Other requirements that bite: 5.2.1 size limit (L1), 5.2.2 type and content check, all files at L2 (L1), 5.2.3 compressed size and file-count limits (L2), 5.2.4 per-user quota (L3), 5.2.6 pixel-size limit (L3), 5.4.3 antivirus on untrusted files (L2); 8.2.2 object-level access control (L1), 8.3.1 enforce at a trusted layer (L1), 8.3.3 access based on the originating subject, not the intermediary (L3); 7.2.2 session tokens are not static API secrets (L1); 13.3.1 secrets management (L2); 3.4.3 Content-Security-Policy (L2); 3.5.4 separate applications on separate hostnames (L2); 12.3.1 and 12.3.3 TLS for internal connections too (L2); 15.1.2 SBOM (L2); 16.3.1 and 16.3.2 log authentication and failed authorization (L2); 2.4.1 anti-automation (L2); 2.3.5 multi-user approval for high-value flows (L3). Sources: the ASVS 5.0 chapter files under https://github.com/OWASP/ASVS/tree/master/5.0/en/. Confidence: primary.
- OWASP Top 10:2025 is the current edition (the eighth). A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions (new: failing open, bad error handling). Sources: https://top10.owasp.org/2025/0x00_2025-Introduction/, https://owasp.org/projects/top-ten. Confidence: primary.

### Implication for Phyllon

- Target ASVS 5.0.0 level 2 for the whole application, plus three level 3 items that match Phyllon's risk: 5.2.4 (upload quotas), 5.2.6 (pixel limits) and 8.3.3 (act with the originating subject's permissions, which is the whole point of an MCP server acting for a user). Inference: L2 is the stated default for "most applications", and children's data plus an approval workflow rule out stopping at L1. Full L3 is not worth a one-maintainer project.
- Keep a status file per requirement (met, not applicable, gap, with a link). ASVS 5.0 expects documented security decisions (permitted file types, authorization rules, log inventory), and writing them also feeds the DPIA material in section 9.
- A01 and A06 are the real risks: profile rules ("may see solutions", "may approve content", "may use admin tools") are access control, so one policy function must decide every read and write across web, upload and MCP paths.
- A10 maps to Rust: no `unwrap` on request paths, and every error path denies by default.

## 2. LLM and agent security

### Facts

- The OWASP Top 10 for LLM Applications 2026 is current, published 3 to 4 August 2026 (the site and the repo differ by a day). Order: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Excessive Agency, LLM04 Supply Chain, LLM05 Data and Model Poisoning, LLM06 Unbounded Consumption, LLM07 Misinformation, LLM08 Hidden Context Exposure, LLM09 Vector and Embedding Weaknesses, LLM10 Improper Output Handling. Sources: https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/, https://github.com/GenAI-Security-Project/GenAI-LLM-Top10. Confidence: primary.
- LLM01 states that no reliable prevention exists because models make no architectural distinction between instructions and data, and that defense is architectural: assume the instruction boundary will be bypassed and constrain what the model can do. It names documents, retrieved passages, tool output and MCP output as injection surfaces, and describes the "trusted surface" attack: text planted through a low-privilege channel (a form, a ticket) is read later by the user's agent running with the user's privileges. Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md. Confidence: primary.
- LLM01 mitigations that apply here: strip tag-block (U+E0000 to U+E007F), variation-selector (U+FE00 to U+FE0F) and zero-width (U+200B, U+200C, U+200D, U+2060) characters at every ingest and render boundary (#5); pass external content through a structurally separate, provenance-labeled channel, which reduces success only against non-adaptive attacks (#6); require human confirmation for privileged or irreversible actions and show the exact rendered action, not a summary, because approval fatigue and invisible characters defeat reviewers (#7); budget agents by the Rule of Two (an agent holding untrusted input, sensitive data and state-change ability at once needs per-action human approval) (#8); treat agent memory writes as privileged (#9); test against adaptive attackers who know the defense (#11). Same source. Confidence: primary.
- LLM03 Excessive Agency: minimize tools, tool functionality and permissions; avoid open-ended tools (shell, "fetch any URL"); execute tools in the user's context and preserve the original user's authorization across chained calls; require approval for high-impact actions; enforce complete mediation in code, not in the model; add monitoring and rate limits. Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md. Confidence: primary.
- LLM10 Improper Output Handling: treat model output as a zero-trust user, encode it for its sink, use parameterized queries, use a strict CSP, and do not auto-render Markdown images or link previews from model output. Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM10_ImproperOutputHandling.md. Confidence: primary.
- LLM09 Vector and Embedding Weaknesses: similarity search often runs over the whole index before access control, which leaks across tenants; embeddings can be inverted to recover text; an attacker who can upload files can poison retrieval so their content ranks for a target query. Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md. Confidence: primary.
- The OWASP Top 10 for Agentic Applications 2026 was published 9 December 2025. Its ten items are ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain, ASI05 Unexpected Code Execution, ASI06 Memory and Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents. Sources: https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/ (date, primary), https://blckalpaca.at/en/knowledge-base/ai-agents/ai-agent-security-owasp/owasp-agentic-asi-top-10-2026 (the item list). Confidence: primary for the date, secondary for the list.
- The OWASP MCP Top 10 is a beta (2025 numbering, "Phase 3 beta release"). Items include MCP01 Token Mismanagement and Secret Exposure, MCP02 Privilege Escalation via Scope Creep, MCP03 Tool Poisoning, MCP06 Prompt Injection via Contextual Payloads, MCP07 Insufficient Authentication and Authorization, MCP08 Lack of Audit and Telemetry, MCP10 Context Injection and Over-Sharing. Source: https://owasp.org/projects/mcp-top-10. Confidence: primary (beta status noted).
- The OWASP MCP Security Cheat Sheet (references spec 2026-07-28) says: treat every tool response as untrusted data even from approved servers; label tool data as data; tag stripping and pattern detection are only extra filtering; enforce authorization in application code independent of the model; for retrieval tools extract structured data instead of passing raw HTML; validate `Origin`. Source: https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html. Confidence: primary.
- OWASP also publishes "A Practical Guide for Secure MCP Server Development" (February 2026) and AISVS 1.0, a verification standard for AI applications with three levels and chapters on input validation, access control and identity, and memory, embeddings and vector stores. Sources: https://genai.owasp.org/resource/a-practical-guide-for-secure-mcp-server-development/, https://owasp.org/projects/artificial-intelligence-security-verification-standard-aisvs-docs. Confidence: primary (I read the summaries, not the full guide).

### Implication for Phyllon

- Phyllon is the "trusted surface" in LLM01 terms: uploads, chat submissions, web finds and imports are low-privilege channels, and the data later reaches model contexts of other people, possibly with admin tools in reach. Design for "an injection will succeed" and bound what it can do.
- The admin MCP (read untrusted content, see children's data, change state) meets all three parts of the Rule of Two. Per-action human approval in the web UI is therefore mandatory, and it matches the planned design. The approval screen must show the exact stored text after normalization, with invisible characters revealed, not a model-written summary.
- Keep untrusted ingestion and admin authority apart: an AI client that performs "web finds" should not hold the admin token. Use separate MCP resources and tokens (section 3).
- Tool design per LLM03: narrow typed tools, no "run SQL" or "fetch URL" tool, input schemas validated server-side, per-tool rate limits, every call mediated by the same policy function as the web UI.
- Mark every content item with origin (upload, chat, web, import) and a trust flag. Content never becomes visible to other profiles' model contexts until a person approves it. Approval is a security boundary, not a quality step.
- Strip the listed invisible code points at ingest and again at render and at MCP output. Wrap MCP output in a labeled data field and never emit auto-loading URLs or raw HTML.
- Permission checks for search belong inside the SQL query, before ranking (LLM09). Solutions must never appear in snippets, embeddings, error messages or similarity results for a profile without the "may see solutions" rule. Treat embeddings as sensitive as the source text.

## 3. MCP security

### Facts

- The current MCP revision is 2026-07-28. It has no protocol-level sessions: servers that need state mint an explicit handle and receive it back as a tool argument. A server that supports only this revision should ignore a stray `Mcp-Session-Id` header and not mint session IDs. Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http, https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices. Confidence: primary.
- State handle hijacking (the successor to session hijacking): servers must verify every inbound request and must not treat possession of a handle as authentication; handles should be non-guessable and bound server-side to the authenticated user (for example key by `<user_id>:<handle>` with the user ID from the verified token). Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices. Confidence: primary.
- Multi Round-Trip Requests: a server must treat `requestState` as attacker-controlled and protect its integrity (HMAC or AEAD). It should bind the principal, a short expiry and the originating request, and must enforce single use itself when needed. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr. Confidence: primary.
- Token passthrough is an anti-pattern: servers must not accept tokens that were not issued for them, and must not accept or transit any other tokens. Servers must validate that a token was issued for them as audience (RFC 8707, RFC 9068 `aud`). Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization. Confidence: primary.
- Confused deputy: MCP proxy servers that use a static client ID with a third-party authorization server must obtain user consent for each dynamically registered client before forwarding. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations. Confidence: primary.
- SSRF: clients fetching OAuth URLs must consider SSRF. Mitigations: HTTPS only (loopback excepted), block private, loopback and link-local ranges including cloud metadata (169.254.0.0/16), do not hand-roll IP parsing (octal, hex and IPv4-mapped IPv6 tricks), do not blindly follow redirects, consider an egress proxy such as Smokescreen, pin DNS results against TOCTOU rebinding. The same applies to an authorization server that fetches Client ID Metadata Document URLs. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices; RFC 9728 section 7.7, https://www.rfc-editor.org/rfc/rfc9728.txt. Confidence: primary.
- Scope minimization: start with minimal read scopes, elevate through targeted `WWW-Authenticate` `scope` challenges, accept down-scoped tokens, log elevation. Common mistakes: publishing every scope in `scopes_supported`, wildcard or omnibus scopes, treating token-claimed scopes as sufficient without server-side authorization. A client without a `scope` challenge falls back to requesting all of `scopes_supported`. Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization. Confidence: primary.
- Streamable HTTP: servers must validate `Origin` on all connections and answer a present but invalid `Origin` with 403 (DNS rebinding defense); authentication should cover all connections; local servers bind to localhost. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http. Confidence: primary.
- Tools: servers must validate all tool inputs, implement access controls, rate limit invocations and sanitize outputs; clients should confirm sensitive operations. Source: https://modelcontextprotocol.io/specification/2026-07-28/server/tools. Confidence: primary.
- Elicitation URL mode sends the user out of band to a URL for sensitive interactions that must not pass through the client. It must not be used to authorize the user to the MCP server itself. Source: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation. Confidence: primary.
- Server that is its own authorization server, what the spec requires. The authorization server must implement OAuth 2.1 and publish RFC 8414 metadata or OIDC discovery. The MCP server must serve RFC 9728 Protected Resource Metadata with an `authorization_servers` field, announced through `resource_metadata` in the `WWW-Authenticate` header of a 401 or at a well-known URI (path-suffixed or root). Clients must send PKCE with `S256`, must refuse to proceed if `code_challenge_methods_supported` is absent, must send the RFC 8707 `resource` parameter in authorization and token requests, and must keep tokens out of query strings. Authorization servers must validate exact redirect URIs, should send the RFC 9207 `iss` parameter (a future revision is expected to make it a MUST), should issue short-lived access tokens, and must rotate refresh tokens for public clients. Redirect URIs must be `localhost` or HTTPS. Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations. Confidence: primary.
- Client registration: Client ID Metadata Documents (CIMD) are a SHOULD, pre-registration is supported, Dynamic Client Registration (DCR) is a MAY and marked deprecated. An authorization server advertises CIMD with `client_id_metadata_document_supported: true`. For CIMD it must fetch the URL, check the `client_id` equals the URL exactly, check `redirect_uris`, and should apply SSRF protections and show the redirect hostname, with extra warnings for localhost-only redirects. The spec cites `draft-ietf-oauth-client-id-metadata-document-00`; the datatracker shows revision 02 (2026-07-06). Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration, https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/. Confidence: primary.
- What the named clients do. Claude (claude.ai, Desktop, mobile and Claude Code) uses CIMD only when the authorization server metadata advertises `client_id_metadata_document_supported: true` and lists `"none"` in `token_endpoint_auth_methods_supported`; otherwise it falls back to DCR. Claude Code uses its own CIMD and a loopback redirect that needs a port-agnostic match for `localhost` and `127.0.0.1`. Claude requires a 401 to start sign-in, uses only the first `authorization_servers` entry, always sends PKCE S256, does not support `client_credentials`, and registers a new client on every fresh DCR connection. Source: https://claude.com/docs/connectors/building/authentication. Confidence: primary.
- Open WebUI offers "OAuth 2.1", which uses DCR, and "OAuth 2.1 (Static)", which uses a pre-created client ID and secret. The page does not mention CIMD. It also offers Bearer, Session and plain OAuth modes. Source: https://docs.openwebui.com/features/extensibility/mcp/. Confidence: primary.
- Codex CLI: `codex mcp login` reads `/.well-known/oauth-authorization-server`, binds a loopback callback on a random port unless configured, and also supports a bearer token from an environment variable. Whether it uses DCR or CIMD was not stated. Source: https://codex.danielvaughan.com/2026/05/19/codex-cli-mcp-server-management-cli-commands-oauth-streamable-http-production-patterns/. Confidence: secondary, DCR and CIMD support unverified.

### Implication for Phyllon

- Treat the normal MCP endpoint and the admin MCP as two resources with two canonical URIs (for example `https://host/mcp` and `https://host/mcp/admin`), each with its own Protected Resource Metadata at the path-suffixed well-known URI. Tokens carry the audience, the resource server rejects any other audience, and the admin scope is absent from `scopes_supported` of the normal resource. A leaked ordinary token then cannot reach admin tools.
- Offer all three registration paths, because real clients differ: CIMD as the default (Claude, Claude Code), DCR for Open WebUI and others, and admin-created pre-registered clients (Open WebUI static, claude.ai confidential client). Constrain DCR: public clients only, PKCE required, HTTPS or loopback redirects, rate limits, garbage collection of unused registrations, and an always-shown consent screen naming the redirect host (ASVS 10.4.7, RFC 9700 section 2.6).
- Publish `code_challenge_methods_supported: ["S256"]`, `authorization_response_iss_parameter_supported: true`, `client_id_metadata_document_supported: true` and `"none"` in `token_endpoint_auth_methods_supported`. Derive the issuer and resource URIs from one configured public URL, never from the `Host` header.
- The CIMD fetcher is an SSRF sink: one hardened HTTP client, resolved-IP checks after DNS, no redirects, short timeout and body cap. Reuse it for OIDC discovery and JWKS fetches later.
- State handles (upload tickets, pending approvals, MRTR `requestState`) must be random, bound to the token's principal, expiring, and never an authenticator.
- Federation keeps the confused-deputy risk visible: Phyllon must stay the authorization server for MCP clients and use the upstream IdP only as a login step, never forwarding IdP tokens and never accepting them at the MCP endpoint.
- Do not accept cookies on `/mcp` or bearer tokens on cookie-authenticated UI routes. Validate `Origin` on `/mcp`, and send no CORS headers there.

## 4. OAuth and identity

### Facts

- OAuth 2.1 is still an Internet-Draft: `draft-ietf-oauth-v2-1` revision 16, dated 2026-09-03, expiring 2027-03-07, state "WG Document, I-D Exists" (the IESG has not started processing it). The MCP spec cites revision 13. Source: https://datatracker.ietf.org/api/v1/doc/document/draft-ietf-oauth-v2-1/?format=json. Confidence: primary.
- RFC 9700 (BCP 240, January 2025) is the current security best practice. It requires exact redirect URI matching, CSRF protection, PKCE for public clients, and authorization servers to support PKCE and mitigate downgrade. It forbids the password grant and discourages implicit. Refresh tokens for public clients must be sender-constrained or rotated. Access tokens should be audience- and privilege-restricted, and resource servers must refuse tokens not meant for them. Clients must defend against mix-up (for example with `iss`). Authorization servers should not let clients influence their `client_id` or claims in ways that could be confused with a resource owner. Access tokens must not appear in URI query strings. Source: https://www.rfc-editor.org/rfc/rfc9700.txt. Confidence: primary.
- RFC 9728 (OAuth 2.0 Protected Resource Metadata) is a Standards Track RFC of April 2025. Source: https://www.rfc-editor.org/rfc/rfc9728.txt. Confidence: primary.
- OpenID Connect Core 1.0 (errata set 2, 15 December 2023): only the pair `iss` plus `sub` is a stable, never-reassigned user identifier. `email`, `phone_number`, `preferred_username` and `name` must not be used as unique identifiers, and `email` may be reused across users or change. Source: https://openid.net/specs/openid-connect-core-1_0.html (section 5.7). Confidence: primary.
- ASVS ties in: 10.5.1 nonce, 10.5.2 identify by `sub`, 10.5.3 reject authorization server metadata whose `issuer` differs from the one used to build the URL, 10.5.4 audience equals `client_id`. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x19-V10-OAuth-and-OIDC.md. Confidence: primary.
- VIDIS (Vermittlungsdienst für das digitale Identitätsmanagement in Schulen) is the German schools' identity broker run jointly by the 16 Länder, with the FWU. A service provider connects as an OpenID Connect client and the login goes to the school's state portal. The service-provider whitepaper (version 60, exported 13 August 2024, so possibly stale) lists these claims: `sub` (unique, may be a pseudonym), `schulkennung` (for example DE-BY-12345), `bundesland`, `rolle` (LEHR, LERN or LEIT), and optional `heimatorganisation`, `akronym`, `email` (real or pseudonymized as `...@vidis.schule`), and `vorname` and `nachname` for teachers only. Standard `name`, `given_name`, `email` and `email_verified` scopes are listed as not implemented. Providers get a client ID and shared secret, with separate test, pilot and production systems. Sources: https://www.vidis.schule/Whitepaper-Service-Provider (PDF), https://www.vidis.schule/ (the 16 Länder). Confidence: primary, dated.
- VIDIS review: a provider self-assessment with 63 questions, then a technical and legal review commissioned by the FWU; criteria include data processing inside the EU (6.3 c). The review "ist kein Gütesiegel und keine Zertifizierung". Normal case for pupils is a pseudonym the provider cannot reverse. Schools sign data processing agreements (AVV) with providers, with a planned VIDIS portal feature for that. Sources: https://www.vidis.schule/datenschutz-bei-vidis/, https://service.vidis.schule/. Confidence: primary.
- A consultancy reports that VIDIS delivers only pseudonymized pupil data and that each Bundesland runs its own release process after the technical connection. Source: https://aschemeier.net/vidis/. Confidence: secondary. Univention also sells an "ID Broker" with per-provider pseudonymization for UCS@school: https://www.univention.de/produkte/ucsschool/id-broker/ (secondary).
- Phyllon would register one client per deployment with a broker like VIDIS (Inference: each self-hosted instance is a separate service provider, since the broker issues per-client secrets and redirect URIs and each school or Schulträger signs its own AVV). Confidence: unverified.

### Implication for Phyllon

- Implement the OAuth 2.1 draft's profile now (authorization code with PKCE only, exact redirect URIs, no bearer tokens in URLs, refresh rotation) because RFC 9700 already requires its substance. The draft's status is not a blocker.
- Opaque access tokens stored hashed in PostgreSQL fit a single process that is both authorization and resource server: revocation and rule changes apply at once (ASVS 8.3.2), and no JWT validation pitfalls (ASVS V9) arise. Keep access tokens short-lived (the MCP spec says "short-lived") and rotate refresh tokens. Sender-constrained tokens (DPoP, ASVS 10.3.5 and 10.4.14, level 3) are optional, since I found no evidence that the named clients support them (unverified).
- Data model now, so federation is additive:
  - `users`: internal UUID primary key, no unique constraint on email or username as identity. Email, display name and profile data are optional.
  - `identities`: `user_id`, `issuer`, `subject`, with `UNIQUE (issuer, subject)`, plus created and last-used timestamps and a minimal claims snapshot. Local passwords and passkeys are just another credential type in a separate table, not columns on `users`.
  - `idp_connections`: issuer, client ID, secret reference, allowed `aud`, claim-to-profile mapping rules, provisioning policy (invite only versus create on first login), enabled flag.
  - `api_tokens`, `oauth_clients`, `oauth_grants` reference `users`, never an email.
  - Link an external identity to an existing user only from an authenticated session with fresh re-authentication. Never auto-link by email: that is the classic account takeover.
  - Map IdP claims to Phyllon profile rules through an explicit table. An unmapped claim grants nothing. Never derive admin rules from a free-form claim.
- A broker like VIDIS gives pupils only a pseudonymous `sub`, a school ID and a role. A model that requires email, real name or birth date for a user will not fit. The `rolle` claim (LEHR, LERN, LEIT) can seed a default profile, but the mapping stays explicit.
- Static bearer tokens: the named clients do support them (Claude Code headers, Codex bearer env var, Open WebUI Bearer mode), so keep them, but as personal access tokens with the controls in section 3 and the baseline. See "Where the current design conflicts".

## 5. File uploads

### Facts

- OWASP File Upload Cheat Sheet: allowlist business-critical extensions only and validate after decoding the name; block lists are weak. The `Content-Type` header is attacker-controlled; signature checks help but are easy to bypass; use them together. Replace user filenames with random IDs (UUID). Validate content by type: decode and re-encode images and strip metadata; do not accept ZIP files. Authenticate and authorize uploaders. Store outside the web root, ideally on a separate host. Apply size limits and apply them after decompression using safe size calculation. Offer a way to report illegal content. Source: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html. Confidence: primary.

### Implication for Phyllon

### Facts

Source: https://www.postgresql.org/support/versioning/, https://www.postgresql.org/. Confidence: primary.

Confidence: primary for the file contents; the privilege conclusion is my reading of PostgreSQL's trusted-extension rule (unverified).
- pgvector filtering: with approximate indexes the filter applies after the index scan, so with HNSW, the default `hnsw.ef_search` of 40 and a condition matching 10% of rows, about 4 rows come back on average. Since 0.8.0 `hnsw.iterative_scan` scans further until enough rows pass. For tenant isolation the README suggests list partitioning or separate tables. Source: https://github.com/pgvector/pgvector#filtering. Confidence: primary.

To migrate: set `password_encryption = 'scram-sha-256'`, reset passwords and change `pg_hba.conf` methods. Source: https://www.postgresql.org/docs/current/auth-password.html. Confidence: primary.
- PostgreSQL 15 removed the default CREATE privilege on the `public` schema for PUBLIC in new databases. Source: https://www.postgresql.org/docs/current/release-15.html. Confidence: primary.

Source: https://www.postgresql.org/docs/current/ddl-rowsecurity.html. Confidence: primary.
- With a connection pool that uses one role, a per-request user needs a setting such as `set_config('app.user_id', ..., true)` (transaction-local) so it cannot leak to the next client. This is common practice, not in the PostgreSQL docs. Confidence: unverified.

### Implication for Phyllon

- Support PostgreSQL 17 and 18 (test both), pgvector 0.8.x, and say 14 is unsupported. Pin the image tag.
- Authentication: `password_encryption = scram-sha-256`, `pg_hba.conf` with `scram-sha-256` only, no `trust` and no `md5`, database reachable only on the internal network.
- Three roles: a bootstrap superuser used only by an init script that runs `CREATE EXTENSION vector`; a schema owner role for migrations (run as a separate step, not by the web process); a runtime role with DML only, without `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `BYPASSRLS` or DDL. Revoke UPDATE and DELETE on the audit table from the runtime role.
- RLS verdict: defense in depth on a few tables, not the primary control. Phyllon's rules are per-profile and multi-dimensional, so policies would need joins to the profile tables, which RLS handles poorly (performance, race conditions, covert channels), and a connection pool needs transaction-local settings on every checkout. The primary control is one repository layer where every query takes a principal and the visibility predicate is part of the SQL (also for vector search). Add RLS with `FORCE` and a runtime role without `BYPASSRLS` only where a policy is a one-column check, for example `owner_user_id` on API tokens, pupil answers and progress, and the audit log. Test with a query that omits the predicate and confirm it returns nothing.
- For ranked search, apply the profile filter in SQL and turn on `hnsw.iterative_scan`. Do not filter the top-k in Rust after the fact, which both under-returns and leaks. Partitioning per user is not needed at family scale.
- Disk encryption, encrypted backups and TLS to the database are deployment guidance, not Phyllon features. Document them.

- The data protection authorities' guidance for online learning platforms (DSK Orientierungshilfe, 26 April 2018, dated but still the reference) asks for: pseudonymized user administration; data minimization (few master data, avoid free-text and comment fields); a login name that differs from the display name; no password reset by email alone; a written role and permission concept; administrator and possibly teacher two-factor depending on the DPIA; encrypted transport; logging with retention and a four-eyes review of logs; deletion of pupil learning data at the end of the school year (subject to state retention rules); account deletion when a pupil leaves; no access for external parties in principle. Source: https://www.datenschutzkonferenz-online.de/media/oh/20180426_oh_online_lernplattformen.pdf. Confidence: primary, dated.
- The BSI "Leitfaden zur Entwicklung sicherer Webanwendungen im Bildungsumfeld" (version 1.0, 1 April 2025) is aimed at "Mein Bildungsraum" and builds on IT-Grundschutz and the BSI TLS minimum standard. Source: https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Oeffentliche_Verwaltung/Moderner-Staat/Webanwendungen_Bildungsumfeld.pdf?__blob=publicationFile&v=3. Confidence: primary.
- VIDIS review and contract needs are in section 4 (source and confidence there). A VIDIS review is not a certification.
- Accessibility: public bodies in Germany must meet BITV 2.0 (WCAG 2.1 AA through EN 301 549). EN 301 549 V4.1.1, aligned with WCAG 2.2, was published in September 2026. Sources: https://bitv.de/bitv/anforderungen, https://www.pivotalaccessibility.com/2026/09/en-301-549-v4-1-1-is-published-what-it-means-for-digital-accessibility/. Confidence: secondary.

### Implication for Phyllon

- CRA: Inference, not legal advice. Mika as a private maintainer who does not monetize the project is likely outside the CRA, and the "steward" category covers legal persons. That changes if an association or company takes payment, paid support, hosting fees tied to the product or product-linked donations, or if a company packages Phyllon for schools (then it is a manufacturer with due-diligence duties toward Phyllon). Cheap preparation that also is good security: `SECURITY.md` and a coordinated disclosure path, an SBOM per release, a stated support and security-update policy, secure-by-default configuration (no default passwords, admin MCP off), and signed releases. Ask a lawyer before taking money.
- GDPR roles: the deployer (family, school, Schulträger) is the controller. The Phyllon project is a software supplier, not a processor, as long as it processes no deployer data. Mika's own family use is probably covered by the household exemption (Article 2(2)(c)); a school deployment is not. Ship a data-flow description, a retention setting, a record-of-processing template and a DPIA template so schools can adopt it.
- Data minimization by design (Articles 5(1)(c) and 25): pupil profiles pseudonymous by default (a label, no real name required); no free-text fields that invite personal data, or clear warnings and retention where they exist (chat submissions are one); MCP output carries no personal data beyond the profile label. An AI client's provider receives whatever Phyllon returns, so MCP output is a data transfer to a recipient the deployer must account for. Transfer rules for US providers are the deployer's problem but need a line in the docs (unverified).
- Retention and erasure: per-profile erase and export, a school-year deletion job, account deletion on leaving. Test that embeddings, derived text and original files are deleted together.
- Schools: expect a written role and permission concept (the profile rules documentation can be it), admin two-factor, TLS everywhere, logs with retention, no third-party requests from the UI, EU hosting, an AVV between school and hoster, and a state-specific approval. A VIDIS connection is a later, per-deployment effort.
- Accessibility: aim for WCAG 2.2 AA in the web UI; it is cheap early and expensive late, and children and schools both need it.
- Treat Article 8 as 16 in Germany. For children's own accounts in a family deployment the parent or school creates the account, so Article 8 consent should not be the legal basis; say so in the docs.

## 10. Rust secure coding and API design

### Facts

- ANSSI's "Secure Rust Guidelines" (repo `ANSSI-FR/rust-guide`, book titled "unstable", still being written, no version number; last commit I saw 2026-05-18). Rules from its checklist: use a stable toolchain (DENV-STABLE), track `Cargo.lock` (DENV-CARGO-LOCK), run the linter regularly (DENV-LINTER), vet direct dependencies (LIBS-VETTING-DIRECT) and check them with cargo-audit (LIBS-AUDIT) and cargo-outdated (LIBS-OUTDATED), use overflow-aware arithmetic (LANG-ARITH), limit panics and test array indexing or use `get` (LANG-LIMIT-PANIC, LANG-ARRINDEXING), wrap errors in a custom error type (LANG-ERRWRAP, a recommendation), do not use `unsafe` blocks (LANG-UNSAFE) and encapsulate any that remain (LANG-UNSAFE-ENCP). Sources: https://anssi-fr.github.io/rust-guide/checklist.html, https://github.com/ANSSI-FR/rust-guide. Confidence: primary.
- The Rust API Guidelines checklist groups rules under Naming, Interoperability, Macros, Documentation, Predictability, Flexibility, Type safety, Dependability, Debuggability, Future proofing and Necessities. They target library crates. Source: https://rust-lang.github.io/api-guidelines/checklist.html. Confidence: primary.
- Clippy has restriction lints `unwrap_used`, `expect_used`, `indexing_slicing`, `arithmetic_side_effects` and `undocumented_unsafe_blocks`. Source: https://rust-lang.github.io/rust-clippy/stable/index.html. Confidence: primary.

### Implication for Phyllon

- Phyllon is an application, so adopt the ANSSI rules selectively and the API guidelines only where internal crates are reused. Concretely:
  - `#![forbid(unsafe_code)]` in every Phyllon crate, with a documented exception process.
  - `clippy` in CI with `-D warnings` and `clippy::unwrap_used`, `expect_used` and `indexing_slicing` denied outside tests (a request must never panic; ASVS 16.5.4 wants a last-resort handler, and a catch-panic middleware fits; tower-http offers one, which I did not check). Consider `arithmetic_side_effects` for quota and size math.
  - One crate-level `Error` type that maps to a generic client message and a detailed log line (ASVS 16.5.1).
  - API guideline items worth using: newtypes for IDs and tokens (`UserId`, `ProfileId`, `TokenHash`) so a profile ID never passes as a user ID (type safety), constructors that validate (`C-VALIDATE`), `Debug` implementations that redact secrets, and `Send` plus `Sync` types for the async server. The checklist items `C-NEWTYPE`, `C-VALIDATE`, `C-GOOD-ERR`, `C-SEND-SYNC` and `C-DEBUG` exist.
  - Parameterized SQL only (a compile-time-checked query layer where possible), templates that escape by default, secrets in a wrapper that redacts and zeroes on drop, constant-time comparison for token checks, OS randomness for tokens. These are my recommendations from standard practice (unverified against a standard).
  - Fuzz the parsers Phyllon owns (upload sniffing, URL and metadata parsing, scope strings). Scorecard's Fuzzing check also rewards it.

## Security baseline for Phyllon

Twenty items. Each has a test that passes or fails.

1. **ASVS status file.** `docs/security/asvs.md` lists every ASVS 5.0.0 level 1 and level 2 requirement plus 5.2.4, 5.2.6 and 8.3.3 as met, not applicable or gap, with a link or a recorded decision. Test: a CI script fails if a requirement ID is missing or a gap has no issue link.
2. **Audience-bound tokens, separate admin resource.** Every access token stores the canonical resource URI and the resource server checks it. Test: a token minted for `/mcp` gets 401 or 403 at `/mcp/admin` and the reverse, and `scopes_supported` of the normal resource contains no admin or approval scope.
3. **OAuth server profile.** Authorization code with PKCE `S256` only, exact redirect match, single-use code of at most 10 minutes, no implicit or password grant, `iss` in responses, rotating refresh tokens with an absolute lifetime. Test: replaying a code fails; a request without `code_challenge` fails; a redirect URI differing by a trailing slash fails; metadata contains `code_challenge_methods_supported`, `authorization_response_iss_parameter_supported` and `client_id_metadata_document_supported`.
4. **Client registration and consent.** CIMD, constrained DCR and admin pre-registration all work. DCR accepts only public clients with PKCE and HTTPS or loopback redirects and is rate limited; unused registrations expire. Every first authorization shows a consent screen naming the redirect host; users can list and revoke grants. Test: a client with a `file:` or LAN-IP redirect is rejected; a registration flood is throttled; a revoked grant fails at the next request.
5. **Static tokens are personal access tokens.** At least 256 random bits, a `phy_` prefix, stored only as a hash, shown once, tied to a user or profile principal, default expiry of at most 90 days, a scope ceiling that excludes admin and approval, a last-used timestamp, revocable. Test: a database dump contains no usable token; a static token cannot call an admin tool or approve; an expired token fails.
6. **One authorization function.** Every read and write on web, upload and MCP paths goes through a single policy check with a principal, and list and search queries put the visibility predicate in SQL. Test: a generated matrix of profiles and rules over every endpoint and tool shows no object, snippet, embedding hit or error text reaches a profile without the matching rule (especially "may see solutions"); a hidden item's existence is not distinguishable.
7. **Approvals out of band.** Admin MCP tools can only create pending requests. Approval needs an authenticated browser session with CSRF protection and fresh authentication, shows the exact normalized text with invisible characters revealed, and the approver is not the submitter. Admin tools cannot change profile rules, tokens, clients or identity providers. Test: no bearer-token path moves an item to approved; no admin tool grants itself more rights.
8. **Untrusted-content handling.** Every item has an origin and trust flag; unapproved content is never returned to other profiles. U+E0000 to U+E007F, U+FE00 to U+FE0F, U+200B, U+200C, U+200D and U+2060 are stripped at ingest, render and MCP output. MCP output wraps content in a labeled data field with no raw HTML or auto-loading URLs. Test: a corpus of injection strings and hidden-character payloads (including through a PDF) comes out clean and labeled; unapproved items are absent from another profile's MCP results.
9. **Outbound requests.** Only one HTTP client may fetch external URLs. It allows HTTPS only, checks resolved IPs against private, loopback, link-local and metadata ranges, does not follow redirects, and has timeouts and a size cap. The web UI makes no third-party requests. Test: fetches to `169.254.169.254`, `[::1]`, a 10.x address and a rebinding hostname fail; a browser run of the UI logs zero third-party requests.
10. **Upload pipeline.** Type by magic bytes against an allowlist (PDF plus tested image types); archives, Office, HTML and EPUB rejected; byte, page and pixel limits and a per-user quota enforced before any parser starts; filenames replaced by UUIDs; EXIF and GPS stripped from stored images; originals served only as attachments with `nosniff`. Test: a ZIP bomb, a polyglot file, a 20000-pixel-wide image, a 5000-page PDF and a photo with GPS data are each rejected or stripped within a set time with no parser started.
11. **Isolated parser.** docling-serve has no route out (internal network only, no published port), non-root, read-only root with tmpfs, `cap_drop: [ALL]`, `no-new-privileges`, memory, CPU and pids limits, an API key, empty CORS, a document timeout of minutes, remote services and plugins off. Test: `curl https://example.com` from inside the container fails; a document built to exhaust memory kills only that container; a stuck parse is cancelled at the timeout.
12. **PostgreSQL hardening.** PostgreSQL 17 or 18; SCRAM-SHA-256 only; no `trust` or `md5` in `pg_hba.conf`; not published on the host; runtime role without superuser, `CREATEDB`, `CREATEROLE`, `BYPASSRLS` or DDL; migrations under a separate owner role; the pgvector extension created by a bootstrap script; RLS with `FORCE` on tokens, pupil answers and audit. Test: `SHOW password_encryption` and a `pg_hba.conf` check in CI; the runtime role fails `CREATE TABLE` and `DROP`; a query without the visibility predicate returns no rows on RLS tables.
13. **Container posture.** The Phyllon image is static, non-root and distroless; read-only root; `cap_drop: [ALL]`; `no-new-privileges`; no privileged mode, host network or container-socket mount; only the proxy publishes a port; secrets as files; images pinned by digest. Compose and Quadlet files both start under Docker and under rootless Podman with SELinux enforcing. Test: CI runs both stacks and a script asserts these properties on `inspect` output.
14. **Rust code policy.** `#![forbid(unsafe_code)]` in all crates; `cargo clippy -D warnings` with `unwrap_used`, `expect_used` and `indexing_slicing` denied outside tests; one error type with generic client messages; a catch-panic layer. Test: CI fails on a deliberate `unwrap()` in a handler; a panicking handler returns a generic 500 and the server keeps serving.
15. **Dependency gates.** `cargo deny check` (advisories, bans, licenses with an AGPL-compatible allow list, sources limited to crates.io) and `cargo audit` on every pull request and nightly; Dependabot for `cargo`, `github-actions` and Docker; all Actions pinned by SHA; default workflow `permissions: contents: read`. Test: a pull request that adds a crate with a known advisory or a GPL-2.0-only license fails; a Scorecard run shows Pinned-Dependencies, Token-Permissions and Dangerous-Workflow at 10.
16. **Signed, attested releases.** Release builds run in GitHub Actions, attach a CycloneDX SBOM, attest provenance and the SBOM with `actions/attest`, sign the container image with cosign keyless, and use immutable releases. Test: a post-release CI job runs `gh attestation verify` on the artifact and `cosign verify` with the repository's workflow identity and issuer, and fails the release if either fails.
17. **Repository hygiene.** `SECURITY.md` with a reporting channel and a support and update policy; GitHub private vulnerability reporting, secret scanning with push protection and CodeQL for Rust on; branch protection on `main`; MFA on the maintainer account. Test: a settings audit through the API in CI, and Scorecard Security-Policy at 10.
18. **Web UI hardening.** `__Host-` session cookie with `Secure`, `HttpOnly` and `SameSite`; CSRF protection on every state-changing form; CSP with `default-src 'self'` and `frame-ancestors 'none'`; `nosniff`, HSTS, a referrer policy; no third-party assets; `Origin` validation and no CORS on `/mcp`. Test: a header-check suite in CI; a cross-site form POST is rejected; a request to `/mcp` with a foreign `Origin` returns 403.
19. **Audit logging without secrets.** Append-only audit events for authentication, token and client creation and use, scope elevation, approvals, admin actions and denied authorization, each with who, what, when and which token ID; no tokens, document text or pupil names in logs; the runtime role cannot update or delete audit rows. Test: after an end-to-end run, a grep of logs for the test tokens and names finds nothing; an `UPDATE` on the audit table fails.
20. **Privacy by design.** Pupil profiles need no real name; MCP output carries only the profile label as personal data; a retention setting and a school-year deletion job exist; per-profile erase and export work; a DPIA template and data-flow document ship with the release. Test: erasing a profile leaves no rows, embeddings, derived text or files for it; the docs files exist and are linked from the README.

## Where the current design conflicts

Each point is what a standard argues against in the project brief. Some are conflicts, some are conditions the design must meet.

1. **Static bearer tokens, "personal or shared per profile".** ASVS 7.2.2 (level 1) says tokens must not be static API secrets for session management, 10.4.9 wants revocation, 16.2.1 wants "who" in every log entry, and OWASP MCP01 and ASI03 flag long-lived and shared credentials. A token shared per profile cannot attribute an action to a person, cannot be revoked for one user, and sits in every client config that uses it. Keep static tokens because Claude Code, Codex CLI and Open WebUI can use them, but make them personal by default, expiring, scoped below admin and approval, and hashed at rest. Allow a shared profile token only for read-only scopes, and log its ID on every use.
2. **"An opt-in admin MCP lets an AI client administer and approve content."** The same agent reads untrusted ingested text, sees children's data and changes state: all three parts of the Rule of Two (LLM01 #8, LLM03). The web-UI confirmation answers the approval half. "Administer" is wider: tools that edit profile rules, mint tokens or clients, change identity providers or approval policy would let an injected agent escalate its own rights. Such tools should be web-only, or each call needs the same out-of-band confirmation. Also keep the "web finds" client and the admin client on separate tokens and audiences.
3. **"Approvals confirmed by a person in the web UI" as a safety net.** OWASP LLM01 #7 warns that approval fatigue and invisible characters defeat reviewers, and that a summary is not the action. If the UI shows a rendered or summarized view, hidden text (white-on-white text in a PDF, tag characters) passes the approval. The UI must show the raw normalized text with invisible characters revealed, and approved content still stays untrusted when it flows into model contexts.
4. **Content from chat, uploads, web finds and imports reaches "later model contexts".** OWASP says there is no reliable prevention; cross-session and cross-user poisoning is a listed scenario (LLM01 scenario 4, LLM09). If any unapproved or partly approved content can reach another profile's model context, the design fails by its own account. Make "approved" a hard gate on visibility to other profiles, and apply the stripping and labeling from the baseline on output.
5. **Everything in one Rust binary on one origin.** ASVS 3.5.4 (level 2) asks for separate applications on separate hostnames so the same-origin policy helps. The web UI (cookie sessions), the OAuth pages, the upload endpoints, the MCP endpoints (bearer) and served uploaded files share one origin in the brief. Untrusted uploads served from the admin origin raise the cost of any XSS or content-sniffing bug. Serve original uploads from a second hostname, or avoid serving them; do not mix cookie and bearer authentication on the same routes.
6. **docling-serve as "a ready-made container".** Defaults are unsafe for untrusted input: a 7-day document timeout, no file size or page limit, no API key, CORS `*`, image sizes from 4.4 GB (CPU) to 8.7 GB (amd64 default), and 28 advisories in five months on the library (memory exhaustion, SSRF, local file read). It is acceptable only if it is treated as a hostile worker (baseline items 10 and 11) and if Phyllon restricts the input formats docling would otherwise accept. Whether it runs with a read-only root and without network has to be tested.
7. **Dynamic client registration and CIMD.** The MCP spec deprecates DCR, but Open WebUI's "OAuth 2.1" mode uses it and Claude falls back to it, so Phyllon cannot drop it. Open DCR is itself a risk (ASVS 10.4.7, RFC 9700 section 2.6) and CIMD turns the authorization server into a fetcher of attacker-chosen URLs (SSRF). The design needs the constraints and the hardened client from the baseline.
8. **"Later it should federate to OIDC."** If the current user table is keyed or uniquely constrained by email or username, federation will force a migration and invite account-takeover-by-email bugs. The model must be `(issuer, sub)` identities linked to an internal user ID now, with no email requirement (VIDIS gives pupils only a pseudonym).
9. **"Profiles made of rules" and tokens.** ASVS 8.3.2 and 8.3.3 and RFC 9700 want rule changes to apply immediately and actions to use the originating subject's permissions. Do not copy profile rules into token claims at issue time; read them from the database on every request.
10. **Children as users with free-text chat submissions.** The DSK guidance asks for data minimization and warns against free-text and comment fields; WP248 treats children as vulnerable data subjects, which together with scoring or AI use makes a DPIA likely for a school. Free text from a child is also an injection channel. Limit, label and expire it.
11. **ASVS 12.3.x (level 2) wants TLS between internal services.** A plain-HTTP link between Phyllon and docling-serve, or to PostgreSQL, on an internal network contradicts it. Either enable TLS or record a deliberate deviation. This is a smaller conflict that the single-host container layout makes easy to ignore.
12. **A conflict the standards do not settle: DPIA and school approval versus a self-hosted open-source tool.** VIDIS and the Länder review providers, and a VIDIS review "is not a certification". A project that publishes only code has no provider for that review; each deployer (or a school authority acting as hoster) must carry it. Say so plainly in the docs instead of implying school readiness.
